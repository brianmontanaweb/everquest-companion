> **For agentic workers:** steps use checkbox (`- [ ]`) syntax. Execute top to bottom; each task ends in its own commit.

## Context

`npm audit` reports **5 vulnerabilities (2 high, 3 moderate)** in this tree. Every one is a
**transitive** dependency — nothing in `package.json` is directly affected — and every one reports
`fixAvailable: true`, meaning the fix lands **inside the semver range the existing parents already
declare**. A verified `npm audit fix --dry-run` confirms the whole remediation is 7 in-range
patch/minor moves, with `added: 0, removed: 0`:

| package | from → to | bump | why it's here |
|---|---|---|---|
| `fast-uri` | 3.1.5 → 3.1.7 | patch | `ajv` → 4× **high** SSRF / host-confusion |
| `nanoid` | 3.3.16 → 3.3.18 | patch | `vite` → `postcss` → **high** infinite loop on size 0 |
| `fflate` | 0.8.1 → 0.8.3 | patch | `@aws-sdk/client-cloudwatch` → `@smithy/middleware-compression` → moderate ZIP64 infinite loop |
| `@smithy/middleware-compression` | 4.5.16 → 4.6.2 | minor | flagged for depending on the vulnerable `fflate` range |
| `@smithy/types` | 4.16.1 → 4.18.0 | minor | collateral of the line above |
| `@smithy/core` | 3.31.1 → 3.33.3 | minor | collateral of the line above |
| `@xmldom/xmldom` | 0.8.13 → 0.8.15 | patch | `electron-builder` → `app-builder-lib` → `plist` → moderate XML fragment injection |

**There are no major-version updates in this remediation.** The user's "take caution, one dependency
at a time" branch does not trigger. The one-commit-per-advisory structure below is chosen instead so
that a regression in the build, the Lambda bundle, or packaging is attributable to a single bump
without unpicking a 7-package lockfile diff.

**Outcome:** `npm audit` reports 0 vulnerabilities, `package.json` is byte-identical, and the four
commits sit on an unmerged branch for the owner to review.

### Honest severity note (do not silently "fix" this away)

`@xmldom/xmldom` is reachable only through `node_modules/app-builder-lib/out/util/plist.js` and
`macosIconComposer.js` — **macOS-only code paths**. This project builds `nsis` and only `nsis` on
Windows, so the advisory is not exploitable here. It is still worth clearing (it is free, and it
keeps `npm audit` at zero so the *next* finding is visible), but Task 4's verification is a
resolution smoke test, not proof of a fixed exploit. Say so in the commit message.

## The lockfile-delta helper (used by every task)

After each `npm update`, run this to see **exactly which packages moved**. `npm update <name>` may
opportunistically move other in-range packages; this is how you catch that instead of discovering it
in a merge review. Save it once and reuse it.

```bash
node -e '
const { execSync } = require("child_process");
const fs = require("fs");
const a = JSON.parse(execSync("git show HEAD:package-lock.json", { maxBuffer: 1e9 })).packages;
const b = JSON.parse(fs.readFileSync("package-lock.json", "utf8")).packages;
for (const k of new Set([...Object.keys(a), ...Object.keys(b)])) {
  const x = a[k] && a[k].version, y = b[k] && b[k].version;
  if (x !== y) console.log(`${k}  ${x} -> ${y}`);
}'
```

**If a package moves that the task does not list as expected, stop and report it** rather than
folding it into the commit.
