# Prettier setup — EQ Legends Companion

Branch: `tooling/prettier-setup-2026-09-13`. Task list: [2026-09-13-prettier-setup-todo.md](2026-09-13-prettier-setup-todo.md).

## Context

A prior TypeScript/tooling audit of this repo found no formatter wired in at
all — the ~54k-line tree had a consistent de-facto style (no semicolons,
single quotes, lines running well past 80 chars) enforced by nothing but
habit and ESLint's incidental overlap. The owner asked to close that gap and
settled four decisions up front:

1. **Style — match the existing code, not Prettier's defaults.** Verified
   against `src/main/windows.ts` and others: `semi: false, singleQuote: true,
   trailingComma: 'all', printWidth: 100, tabWidth: 2, endOfLine: 'lf'`. JSX
   already uses double quotes in the tree, which is Prettier's default
   regardless of `singleQuote`, so no override was needed.
2. **Reformat the whole tree now, in one commit**, not incrementally —
   matching this repo's "debt only shrinks, never sits half-migrated" stance
   (the ESLint ratchet, the Rust factoring ratchet). A
   `.git-blame-ignore-revs` entry keeps `git blame` useful afterward.
3. **Add husky + lint-staged now**, a real departure from this repo's
   previous CI-only enforcement pattern, chosen deliberately by the owner —
   auto-formats staged files pre-commit. CI's `prettier --check` still gates
   as a backstop for anyone who bypasses the hook or hasn't run the one-time
   local setup step (`.npmrc`'s `ignore-scripts=true` blocks the usual
   automatic husky install, same reason `deps:electron` is a manual step).
4. **Format source code only** —
   `.ts/.tsx/.mts/.cts/.js/.jsx/.mjs/.cjs` — mirroring exactly what
   `eslint.config.mjs` already lints. `*.json`, `*.yml`, and `*.md` stay
   untouched.

`eslint-config-prettier` was added as a safety net alongside the formatter
(no active conflict exists today — typescript-eslint's presets carry no raw
formatting rules — but this stops one from being silently reintroduced
later). Enforcement is CI-only backstop (`prettier --check` in `build.yml`,
alongside the existing typecheck/lint/audit steps) plus the local pre-commit
hook, matching this repo's existing "gate in CI, never trust a habit"
philosophy (see the `npm audit` step's own rationale in `build.yml`).

Executed and committed in dependency order on one branch — config wired
first (so `format:check` could be verified failing-as-expected before the
rewrite), then the mass reformat as its own dedicated commit, then blame
suppression, then the two enforcement layers, then documentation — matching
this repo's own `security/audit-fixes-2026-09-12` precedent (one branch,
commits per step, PR opened, **not merged** — merge is the owner's call per
AGENTS.md's branch-integration rules).

## Config + ESLint compatibility layer

`prettier.config.mjs` pins the four style values above. `.prettierignore`
mirrors `eslint.config.mjs`'s `IGNORES` array entry-for-entry, plus the two
files pinned byte-for-byte by their own tests
(`src/shared/dataServer/protocol.generated.ts`, `eslint.ratchet.mjs` — the
latter is regenerated by `scripts/lint-report.mts`, so reformatting it would
just be undone by the next `npm run lint:ratchet`). `format` / `format:check`
scripts were added next to the existing `lint` script family.
`eslint-config-prettier` was wired into `eslint.config.mjs` as its own
layer, placed after the correctness layer so it can override anything that
layer sets, with a comment explaining it's defensive rather than fixing a
live conflict. Verified wiring with no source changes yet: `typecheck` and
`lint` stayed clean, `format:check` failed across most of the tree as
expected — confirming the tool was scanning the right files before the
rewrite touched anything.

## Mass reformat

`npm run format` rewrote every tracked, non-ignored source file in one pass.
Spot-checked across every top-level directory with `git diff -w` to confirm
each changed line was whitespace/quote/semicolon/trailing-comma only, never
a semantic change. `npm run typecheck` stayed clean throughout. `npm run
lint` and `npm test` surfaced real, unanticipated fallout at this step —
see the `-todo.md` companion for the full account of what that fallout was
and how it was resolved; it was materially larger and stranger than this
plan anticipated ("possibly a couple" ratchet entries, not 114 lint errors
and 12 broken test regexes) and needed owner rulings before the commit
could land clean.

## `.git-blame-ignore-revs`

Records the mass-reformat commit SHA(s) so `git blame` (and GitHub's web
blame) skip over the pure-formatting diff and attribute lines to the commits
before it. GitHub's web UI reads this file automatically once it's at the
repo root; local `git blame` needs a one-time
`git config blame.ignoreRevsFile .git-blame-ignore-revs` per clone
(documented in AGENTS.md).

## husky + lint-staged (local pre-commit auto-format)

`npx husky init` wired `.husky/pre-commit` and `git config core.hooksPath
.husky`; the hook body runs `npx lint-staged`, scoped in `package.json` to
`prettier --write` only — not `eslint --fix` — since auto-fixing lint on
commit would risk silently interacting with ratchet entries in ways that
contract reserves for the integrator, not a pre-commit hook. `ignore-scripts
=true` in `.npmrc` means the usual automatic husky install via `prepare`
never fires on a fresh `npm ci`; AGENTS.md's Toolchain-gotchas section
documents the one-time manual `npm run prepare` step, following the same
precedent as `deps:electron`.

## CI enforcement

A `Format check` step (`npm run format:check`) was added to both jobs in
`.github/workflows/build.yml` — `build` and `release` — directly after each
job's existing `Lint` step. The two jobs deliberately duplicate their
prelude (a documented security-boundary reason lives in the file's header),
so the new step was added to both rather than factored into a shared step.

## Line endings (`.gitattributes`) — the half of `endOfLine: 'lf'` that was missing

Not in the original plan; added by the final whole-branch review after CI
failed on it. `endOfLine: 'lf'` is a claim about the **working tree**, because
that is the only thing Prettier reads — the git blob never enters the picture.
Under `core.autocrlf=true` (the Git-for-Windows default, and what GitHub's
`windows-latest` runners use) checkout smudges every unattributed text file to
CRLF, so `format:check` reds the very files it had just formatted. On this
branch's first real CI run that was **1493 files**.

`.gitattributes` therefore now pins `eol=lf` on exactly the extensions
`format`/`format:check` covers — `*.ts *.tsx *.mts *.cts *.js *.jsx *.mjs
*.cjs`, one line each, since `.gitattributes` patterns are fnmatch and have no
brace expansion — extending the file's existing JOS-251 section, which had
already documented this mechanism for three narrower paths. The two files are
a pair: `prettier.config.mjs` says what line endings the tree must have, and
`.gitattributes` is what makes a fresh checkout actually have them. Its
`endOfLine` comment says so, and says what the wrong rationale was.

## The ratchet override

Also not in the original plan, and an owner decision rather than an
implementer's. Task 2's approved 104-entry re-baseline is exactly the case
`scripts/checkLintRatchet.mts` failed unconditionally on, so shipping this
branch meant either a permanently red gate or merging over it. Neither is
acceptable, so the gate gained a machine-readable way to record consent: a
`Ratchet-Widening-Approved:` git trailer on any commit in `<base>..HEAD`.
Found, the growth passes **and is logged in full with the approving commit**;
absent, the previous fail behavior is unchanged. The predicate is exported and
unit-tested. Full rationale in the `-todo.md` companion and in the script's own
header.
